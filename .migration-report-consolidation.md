# Consolidation: Express backend → one full-stack Next.js app

Two processes became one. Every endpoint the Express server at `http://localhost:5000` exposed is
now a Next.js Route Handler under `NextJS/app/api/**/route.ts`, talking to the same PostgreSQL
database (`barber_dev`) through Prisma directly. The browser now calls its own origin, so CORS is
moot and there is nothing left to deploy alongside the frontend.

**`F:\SaloonBookingSystem\backend` was NOT touched.** Not one file under it was created, modified or
deleted — the newest mtime in that tree is still `2026-09-17 17:25`, from before this work started.
It remains a working, runnable reference/fallback. `F:\SaloonBookingSystem\Frontend` was likewise
left alone.

### Middleware without middleware

Express gave two things away for free that a Route Handler has to ask for:

- **`zodMiddleware.validate()`** → `parseJsonBody(request, schema)`. On failure it returns exactly
  what the Express version returned: HTTP 400 with body `{"message": "Give Proper Validations"}` —
  no `success` field, because the original had none and the client's `createAppointment` already
  handles that shape. **It hands back the RAW body, not Zod's parsed output**, because the Express
  middleware only ever *validated* `req.body`, never reassigned it. Returning parsed output would
  have silently applied `.trim()` and `.default("any")` where the controllers previously saw raw
  values — a behaviour change disguised as a port.
- **`errorHandler`** → `handleRouteError(error)`, called from every handler's `catch`. Same four
  branches in the same order: exclusion violation → 409 slot-taken, `AvailabilityError` → its own
  status, Prisma `P2025` → 404, Prisma `P2002` → 409.

### Two shapes for service/settings reads, on purpose

`listServices()` / `loadSettings()` return **raw Prisma rows** — that is what the Route Handlers
serialise, preserving the exact wire format the Express backend produced (`price` as the Decimal
string `"150"`, `@db.Date` as a full ISO datetime). `lib/api/normalize.ts` on the client already
knows how to read that, so nothing was pre-normalised server-side, exactly as the brief specified.

`listActiveServicesView()` / `getSalonSettingsView()` return the plain domain types with `price`
already a number — for Server Components, which bypass the HTTP layer and therefore never get the
client-side normaliser. Without this, a Prisma `Decimal` object would reach `formatPrice()` as `NaN`.

## 4. The `excludeAppointmentId` fix

**The bug.** `GET /api/barbers/:id/availability` had no way to leave an appointment out of the
overlap check, while the reschedule *write* path (`PATCH /api/admin/appointments/:id` →
`resolveBooking({ excludeAppointmentId })`) always did. The read and the write disagreed: with the
current barber and day still selected, an appointment blocked its own slot in the grid the admin was
looking at. `computeAvailability` / `computeAvailabilityDetailed` / `loadContext` already threaded
the parameter — only the HTTP surface never exposed it.

**The fix.** `excludeAppointmentId` is now a query param on both availability routes:

- `app/api/barbers/[id]/availability/route.ts`
- `app/api/availability/route.ts` (for parity — an "any barber" reschedule)

and is forwarded by `lib/api/barbers.ts`'s `getBarberAvailability` and `lib/api/availability.ts`'s
`getAvailability`.

**Why it was worth doing properly.** The old client-side workaround could only recover *one* slot —
the appointment's own start. Every *other* slot the appointment overlapped stayed greyed out. Measured
live during verification, on a 30-minute appointment at 16:00 with a 15-minute grid:

```
own slot 16:00: available WITHOUT exclude = false, WITH exclude = true
bookable slots: 21 without exclude  ->  23 with exclude   (+2)
```

The workaround recovered 16:00. It could not recover 15:45 or 16:15. A 45-minute appointment loses
four. That is a front desk being told times are taken when the server would happily accept them.

**What changed in `components/admin/RescheduleDialog.tsx`:**

- The fetch passes `excludeAppointmentId: appointment.id` (and `appointment.id` joined the deps array).
- **Removed** the availability override `available: slot.available || isCurrent` — the server now
  reports the truth, so the client no longer second-guesses it.
- `isCurrent` survives, downgraded to what it should always have been: a *label* ("current") marking
  where the appointment stands today, and the input to the `isUnchanged` check. It no longer
  overrides availability.
- The header comment's "ONE HONEST LIMITATION" paragraph was replaced with a description of the fix.

A regression test for this went into `test/doubleBooking.test.ts` — it asserts both the own slot and
an overlapping neighbour come back free with the parameter, that the total slot count is unchanged,
and that the write path then actually accepts a move onto the overlapping slot.

**The client contract did not change.** Not one response shape, envelope or field name was altered —
only where the fetch goes. Every `lib/api/*` function still unwraps the same `{success, …}` bodies and
runs the same `normalize*` passes.

`app/page.tsx` was the **only** server component making HTTP calls, so it is the only one refactored.
A Server Component fetching its own Route Handler over loopback is a pointless round-trip that also
needs an absolute URL the app does not reliably know at build time. Client Components — the booking
wizard and the whole admin dashboard — correctly keep using the `fetch`-based `lib/api/*` functions:
they run in the browser and have no other way to reach the server. Both reads stay wrapped in
`.catch()` so a database outage degrades the landing page to its static copy rather than failing the
prerender, and `export const revalidate = 300` is unchanged.

## 6. bcrypt vs bcryptjs — switched, and verified against real hashes

**Switched to `bcryptjs`.** `bcrypt` is a native addon (`bcrypt_lib.node`); shipping native binaries
through a serverless build means the tracer has to resolve the right prebuilt for the deployment's
libc and architecture, which is not the machine the package was installed on. `bcryptjs` is pure
JavaScript and has no such failure mode.

The risk with swapping is that existing password hashes stop verifying, so that was checked against
the live database rather than assumed:

```
hash prefix:                        $2b$10$
bcryptjs compareSync(correct pw):   true
bcryptjs compareSync(wrong pw):     false
bcryptjs self round-trip:           true
```

`bcryptjs` reads the `$2b$` hashes the native `bcrypt` wrote. The seeded owner account logs in
through the new `POST /api/auth/login` with its original password — confirmed again in the browser
during end-to-end verification.

## 7. Login rate limiting — NOT carried over

**Called out explicitly, because it is a real reduction in protection.**

The Express app wrapped `/api/auth/login` in `express-rate-limit` (10-minute window, 20 requests).
That middleware keeps its counters in the process's memory, which means nothing in a serverless
deployment where each request may land on a fresh instance — it would not fail loudly, it would just
quietly stop limiting anything. A correct replacement needs shared external state (Vercel KV,
Upstash, or a counter table in Postgres), i.e. a new dependency and new infrastructure, which the
brief placed out of scope.

So the only credential-checking endpoint in the app currently has **no brute-force guard**. This is a
tracked follow-up, not an oversight. The gap is documented in the header comment of
`app/api/auth/login/route.ts` so it cannot be lost.

## 8. Other known gaps

**Outbound email is a stub.** `backend/util/appointmentBookedMail.js` and `forgotPasswordMail.js`
(nodemailer) were not ported; `lib/server/mail.ts` keeps the call sites and their "must never fail a
booking" contract but returns `{skipped}`. Both were *already* no-ops in this environment —
`SMTP_USER`/`SMTP_PASS` are blank in `backend/.env.development`, and the booking mailer returns
`{skipped: 'no SMTP configuration'}` in that case — so behaviour here is unchanged. Email delivery
was not in the brief; porting nodemailer (or moving to a serverless-friendly provider) is a
follow-up, flagged with a `TODO` in the file.

**Validation failure messages are unhelpful — deliberately.** A failed schema parse returns
`{"message": "Give Proper Validations"}`, byte-for-byte what `zodMiddleware.js` returned. It is a poor
message, but improving it is a contract change, and the brief said port faithfully. Worth revisiting
separately.
