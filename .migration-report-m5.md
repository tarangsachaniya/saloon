## 2. Fixes to the M4 foundation

All four were found by pointing the code at the *live* API rather than at assumed shapes. Each is
fixed where it lives, not worked around in M5 code.

### Fix 1 — `price` is a string on the wire (`lib/api/normalize.ts`, wired into `services.ts` / `appointments.ts`)

`types.ts` declares `price: number`. The API actually returns `"price": "300"` — Prisma serialises a
`Decimal` column as a JSON string. Verified:

```
GET /api/services      -> {"name":"Haircut", ..., "price":"300", ...}
POST /api/appointments -> {"appointment":{..., "price":"300", ...}}
```

This type-checks cleanly everywhere while being false at runtime: `a.price + b.price` would
string-concatenate and `price.toFixed(2)` would throw. M5 only displays the price, so I could have
patched `formatPrice` alone — but that leaves a live landmine for M6's admin totals. Normalising at
the API boundary instead makes the declared type honest for *every* consumer, so I added
`normalizeService` / `normalizeAppointment` and wired them through all service and appointment
readers (admin ones included — they are `lib/api`, not `app/admin`, so M6's diff stays clean).

### Fix 2 — `appointmentDate` is an ISO datetime, not `"YYYY-MM-DD"` (same file)

```
POST /api/appointments -> "appointmentDate":"2026-09-22T00:00:00.000Z"
```

`types.ts` promises `DateString`. Feeding the ISO form to `fromDateString` gave
`Number("22T00:00:00.000Z")` → `NaN` → **"Invalid Date"** on the confirmation screen. `toDateOnly`
slices the first 10 characters rather than doing `new Date(value)` + local getters, because the API
sends midnight **UTC** — re-parsing it anywhere west of Greenwich would silently move the
appointment back a day, which is exactly the bug `toDateString` exists to prevent.

### Fix 3 — `fromDateString` hardened (`lib/utils/time.ts`)

Same root cause, belt-and-braces at the parsing helper: it now slices to 10 chars, so any
un-normalised date string (e.g. `BarberDayOff.date`, which `getBarber` does not yet normalise)
formats correctly instead of rendering "Invalid Date". One-line change, no behaviour change for
well-formed input.

### Fix 4 — currency was EUR for an Indian salon (`lib/utils/format.ts`)

M4 left `CURRENCY = "EUR"` with the comment *"a single place to change once the salon's currency is
confirmed"*. The seeded salon is unambiguously Indian — `"12 MG Road, Bengaluru, India"`,
`+91 98765 43210`, prices 100–800 — so the placeholder rendered a ₹300 haircut as **"€300.00"**, a
100x misstatement of price on a customer-facing booking screen. Changed to `INR` / `en-IN`, and
`formatPrice` now shows paise only when non-zero (`₹300`, `₹250.50`). Trivially reversible if the
currency was meant to stay EUR.

`formatPrice` also widened to `number | string` as a display-layer safety net behind Fix 1.

### Not fixed (reported, not touched)

- **`lib/booking/types.ts`** got doc comments on `Service.price`, `Appointment.appointmentDate`,
  `Appointment.price` and `BarberDayOff.date`. No signatures changed.
- **`getBarber` does not normalise `daysOff[].date`.** M5 never reads it (the availability endpoint
  applies days off server-side), so I left it alone and documented it on the type instead.
- **No UI-kit gaps found.** `Calendar` already had exactly the `minDate` / `maxDate` /
  `isDateDisabled` props this milestone needed, and `maxBookableDate` was the right helper. No
  `components/ui/*` file was modified.

## 4. Judgment calls

**Stepper UX.** Six labelled steps do not fit across 375px, and a horizontally-scrolling strip hides
progress off-screen. So the stepper degrades instead of scrolling: a always-visible
"Step 3 of 6 · Choose a date" line plus a progress bar (the information that actually matters on a
phone), a row of six 40px circles inside ~56px touch targets (six fit at 375px without labels), and
step names that appear only at `sm` and up. Each circle is a real `<button>` with an
`aria-label` like "Step 4: Choose a time (completed)" and `aria-current="step"`.

**Explicit current step, not derived.** `app/book/page.tsx` tracks the step in local state rather
than deriving it as "the first incomplete step". Deriving would make backward navigation impossible —
stepping back to change the service would immediately bounce the customer forward again to the first
gap. Backward moves are free; forward jumps go through the context's `canGoToStep`.

**The clamp effect.** Because every selection invalidates what follows it (the context clears
barber/date/slot when the service changes), an explicit step can be stranded on a screen whose data
no longer exists. An effect walks it back to the first incomplete step.

**`advance()` deliberately bypasses `canGoToStep`.** I hit this as a real bug mid-build: the
selection that unlocks the next step happens in the *same event* as the advance, so `canGoToStep` —
closed over the pre-update context value — still reported the next step as unreachable and silently
swallowed every advance. `goTo` (stepper, "Change" links) stays gated; `advance` (called by a step
component that just made its selection) is not, with the clamp as the backstop.

**Closed-day date picker.** Days are disabled by **weekday** only, cross-referencing
`openingHours[].isOpen` — verified: all Sundays struck through. Deliberately *not* by barber day-off:
a barber's days off are not exposed on the public list endpoint, and greying a date out because one
barber is away would hide dates that are genuinely bookable with someone else (or with "Any
barber"). Those surface honestly one step later as "No times available on this day", which also tells
the customer *why*.

**Inline `Calendar`, not the `DatePicker` popover.** In a wizard the calendar *is* the step; a
popover adds a tap and an overlay that behaves poorly on small screens. `DatePicker` remains the
right component for forms (M6's reschedule dialog).

**Slot grid preserves the backend's two distinct meanings.** A time *missing* from `slots` (the
duration will not fit before closing) is not rendered — offering it would be a lie — while a time
*present* with `available:false` (taken / break / inside the advance window) is rendered greyed,
dashed and struck through but still visible, so the shape of the day reads correctly. A caption
explains both cases: *"Crossed-out times are already booked or fall in a break. Times that are not
listed at all cannot fit a 30 min appointment before closing."* Both are non-clickable.

**`SelectableCard`.** The UI kit's `Card` renders a `<div>` and `interactive` only styles hover.
Rather than bolting `role="button"` + a hand-rolled keydown handler onto a div, the card is wrapped
in a native `<button>` — Enter/Space, focus order, disabled state and the focus ring all come for
free. I chose this over adding an `asChild` prop to `Card` to keep the UI kit untouched.

**`useAsync`.** One small shared hook rather than three hand-rolled `useEffect` + `AbortController`
blocks, so services / barbers / availability get identical loading, error, retry and
cancel-on-change behaviour. In-flight requests abort when the date or barber changes, so a slow
response for an abandoned selection cannot overwrite fresher state. Errors prefer the API's own
human-written message ("Cannot book a date in the past.").

**Home page is a server component on ISR** (`revalidate = 300`). Salon name, hours and prices change
rarely, so serving them from cache keeps the landing page instant; live availability is never shown
there. Both fetches are wrapped in `.catch()` so a backend outage degrades the page to its static
copy instead of failing a production prerender — the M4 comment's concern, addressed rather than
ignored.

**Barber photos.** Seeded photos are all `null`, so the initials avatar is what actually renders. A
photo is passed to `next/image` only when it is an absolute `http(s)` URL: a relative path from the
API would be resolved against the Next origin rather than the API's and 404, so it falls back to
initials instead of showing a broken image.

**Details form is context-driven.** The context holds the field values (so stepping away and back
preserves typing — proven in the race recovery above); only validation errors are local. Validation
runs on submit, and a field's error clears as soon as it is edited — re-validating every keystroke
shouts at people halfway through typing a phone number.

## Concerns

### 1. BLOCKING in a normal browser — backend CORS allowlist excludes port 3001

The wizard's client-side calls **fail in a stock browser** in this environment:

```
GET http://localhost:5000/api/services   (Origin: http://localhost:3001)
  -> Access-Control-Allow-Origin: http://localhost:3000     ← mismatch
```

`backend/config.js:28` → `CORS_ORIGIN: process.env.CORS_ORIGIN || 'http://localhost:3000'`, and
`backend/.env` sets no `CORS_ORIGIN`. Next must run on **3001** here because 3000 is taken by an
unrelated project. The first browser run surfaced this as *"Network error: Failed to fetch"* — which,
to the wizard's credit, rendered as a clean retryable error card rather than a blank screen.

I did **not** fix it: `F:\SaloonBookingSystem\backend` is explicitly out of scope. The fix is one
line by whoever owns the backend:

```
# backend/.env
CORS_ORIGIN=http://localhost:3001
```

then restart the backend. (Server-side fetches — the home page — are unaffected; CORS is a browser
rule.) All browser verification above was done with CORS enforcement disabled in the test browser
only, so the wizard itself is proven; this is purely a config mismatch between the two dev servers.

### 2. Pre-existing: `npm run lint` is broken (M4 scaffold, not M5)

```
TypeError: Converting circular structure to JSON
  at ConfigValidator.formatErrors (@eslint/eslintrc/lib/shared/config-validator.js)
```

`eslint.config.mjs` uses `FlatCompat` + `compat.extends("next/core-web-vitals", "next/typescript")`,
which is incompatible with ESLint 9.39 + eslint-config-next 16. It fails at **config load**, before
any file is linted, so it is unrelated to M5's files and was already broken. Next 16 no longer runs
ESLint during `next build`, so this does not affect the build. I left it alone rather than silently
changing tooling config — it wants a deliberate decision (Next 16 ships a flat config that can be
imported directly instead of via `FlatCompat`).

### 3. Minor

- `middleware.ts` triggers Next 16's *"'middleware' file convention is deprecated, use 'proxy'"*
  build warning. Pre-existing M4/admin code, left untouched (M6's lane).
- Browser verification is Chromium-only; iOS Safari has not been exercised on a real device. Inputs
  use a 16px base font (M4's `FIELD_BASE`) so iOS focus-zoom is already handled.
- The test bookings created during verification ("M5 Probe One", "M5 Browser One", "M5 Race Victim",
  "M5 Race Thief") are live rows in the dev database on 2026-09-22 / 2026-09-23. Harmless demo data,
