## Shared-foundation fixes

Five, each minimal and each reported as required.

### 1. `lib/validation/admin.ts` — a type error that blocked the build

```ts
-  path: ["endTime"] as const,
+  path: ["endTime"],
```

Zod 4 types a refinement's `path` as a mutable `PropertyKey[]`, so the readonly tuple would not
assign. This was pre-existing — the prior agent added these schemas but nothing imported them yet, so
`tsc` only surfaced it the moment the barber schedule editor pulled them in. Two `TS2345` errors,
both gone.

### 2. `lib/booking/types.ts` — `SalonSettings` nullability

`logo`, `phone`, `email` and `address` were declared `string`. They are `String?` in
`prisma/schema.prisma` and the live `GET /api/settings` really returns `"logo": null`. A consumer
writing `settings.phone.replace(...)` or `<img src={settings.logo}>` would have thrown at runtime
while type-checking cleanly — the same class of dishonesty `lib/api/normalize.ts` exists to fix.
Notably `app/page.tsx` had *already* been written defensively (`settings.phone && …`), which is the
tell that M5 hit this in reality. Now declared `string | null`; no call site needed changing.

### 3. `components/ui/DatePicker.tsx` — additive `formatValue` prop

The trigger hard-coded `formatDateLong`. Added an optional `formatValue` so the admin can pass its
own formatter; defaults to the previous behaviour, so every existing caller is untouched. Without
it the reschedule dialog showed "Tue, 22 Sept 2026" in the date field and "Tue, 22 Sep 2026" in its
own header, 200px apart.

### 4. `components/ui/Select.tsx` — additive `aria-label` prop

`Select` supported a visible `label` but had no way to name a label-less instance. The break-row
weekday picker is exactly that case (a label on every repeated row is visual noise), and without
this it shipped with **no accessible name at all**. Mirrors the prop `TimeField` already had.

### 5. `lib/admin/useAdminData.ts` — ref writes moved out of render

```ts
-  loadRef.current = load;          // during render
-  hasDataRef.current = data !== null;
+  useEffect(() => { loadRef.current = load; hasDataRef.current = data !== null; });
```

Two `react-hooks/refs` **errors**. Pre-existing (prior agent's file), but this is M6's own core
infrastructure that all six pages depend on, so it is M6's debt rather than inherited M5 debt. The
sync effect is declared *before* the loading effect deliberately: React fires passive effects in
hook-declaration order within a commit, so the loader always sees refs describing the render that
scheduled it. Verified end-to-end afterwards — every screen still loads, refreshes and mutates
correctly.

### Not fixed, deliberately

`components/booking/useAsync.ts`, `app/book/page.tsx`, `components/booking/ConfirmationSummary.tsx`

## The hydration bug worth calling out

Found by the headless browser, not by the build:

```
+  Fri, 18 Sept 2026      (server render)
-  Fri, 18 Sept, 2026     (client hydration)
```

`formatDateLong` calls `toLocaleDateString(undefined, …)`, which resolves against the *runtime's*
locale and ICU data. Node and Chromium ship different ICU versions, so any admin page with a date in
its `PageHeader` — `/admin` and `/admin/appointments`, both rendered during SSR rather than after a
client fetch — mismatched on every hard load. M5 never hit it because every date in the booking
wizard renders after a client-side load.

Fixed with `lib/admin/format.ts`: a fixed-format, `Intl`-free formatter, now used for every date in
the admin area. **`formatDateLong` was deliberately left alone** — honouring the visitor's own locale
is correct on the customer-facing site, and a single salon's back office loses nothing from a fixed
format.

## Judgement calls

**Diary as a filterable list, not a day×barber grid.** `GET /api/admin/appointments` takes a single
`date` (its `from`/`to` are only consulted when `date` is absent), so a week grid means N requests
per render or client-side bucketing. More to the point, a grid optimises for "find the gap at 3pm
Thursday" — which the booking wizard already does correctly against the server's own availability
engine. The diary's job is different: the day in order, with confirm/arrived/start/complete/cancel
reachable on the row. The barber filter covers the part of a grid that earns its keep. Scope is
therefore **single-day filtering**, as the brief permitted.

**Client detail as a dialog, not a nested route.** The API has no create/update/delete for clients,
so this is a read-only lookup with nothing to lose on dismissal. A modal preserves the search term,
results and scroll position — the actual front-desk interaction ("who is this on the phone… right,
back to the list"). A route would discard that state and add a history entry for a glance.

**Socket.IO: not done.** `socket.io-client` is not installed, and the brief ranks a solid CRUD
experience above it. Every screen has an explicit Refresh button, and `useAdminData` keeps current
data on screen during a re-read (`isRefreshing` separate from first-load `isLoading`) so refreshing
never flashes a spinner or loses scroll position. Mutations also patch their own row locally *and*
trigger a re-read, so the UI is never waiting on a round trip to look correct. Adding the live feed
later is a contained change: subscribe in the diary and the dashboard, call `refresh()` on
`'new Appointment'`/`'appointment Updated'`.

**Deactivate, never delete, in the UI.** The backend 409s a hard delete for anything with
appointment history, and a button that usually fails is worse than no button. `?hard=true` is
reachable through `lib/api` but is not surfaced anywhere.

**Three save buttons on Settings, not one.** Three different schemas, three different occasions to
edit. A new phone number shouldn't be blocked by a half-finished change to Thursday's closing time.

**Reschedule requires a concrete barber** (no "any barber"). The backend would accept `"any"`, but
for a back-office move the admin is deciding *who*, and resolving it server-side would make the slot
grid mean something different from what was clicked.

### One honest limitation, surfaced in the UI

`GET /api/barbers/:id/availability` has no "exclude this appointment" parameter, so when the
reschedule dialog still has the current barber and day selected, the appointment blocks its **own**
slot. Its current start is re-enabled and badged `CURRENT` (the server *does* exclude it on write, so
it genuinely is bookable). Other slots that overlap only this appointment stay greyed out — that
under-offers rather than over-promises, which is the right way to be wrong at a front desk. Visible
in the screenshot: 10:00 AM badged CURRENT, 10:15 AM crossed out.

## Concerns

1. **Socket.IO not implemented** — deliberate, reasoned above. The live-feed hook-up is a contained
   follow-up.
2. **6 pre-existing lint errors remain** in M5/M4 files (`useAsync.ts`, `book/page.tsx`,
   `ConfirmationSummary.tsx`, `AuthProvider.tsx`). Out of scope per the brief, but they are `error`
   severity and will fail a lint gate if CI ever adds one. `useAsync.ts` has the identical
   `react-hooks/refs` issue that #5 fixes in `useAdminData.ts`, so the same three-line fix applies.
3. **Single-day diary scope** — noted above; a range view needs either the `from`/`to` params or one
   request per visible day.
4. **Reschedule under-offers slots** when the current barber+day are still selected — the API has no
   exclude-self parameter. Documented in the UI and in the component. The fix belongs in the backend
   (`computeAvailability` already accepts `excludeAppointmentId` internally; the route just doesn't
   expose it), which is out of scope here.
